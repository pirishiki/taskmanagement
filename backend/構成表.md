バージョンは [README.md の技術スタック](../README.md#技術スタック) にまとめている（Java・Spring Boot・Gradle・PostgreSQL と、主要な部品）。2か所に書くと食い違うもとになるので、ここには書かない。

## プロジェクト構成

| ファイル・フォルダ | 役割 |
| --- | --- |
| `build.gradle` | ビルド定義。使用するSpring Bootのバージョン・依存ライブラリ（Web, Data JPA, PostgreSQLドライバ等）と、静的解析（PMD・Checkstyle）の設定を記述。テスト用の部品（Testcontainers）もここに書く |
| `settings.gradle` | プロジェクト名（`backend`）の定義 |
| `gradlew` / `gradlew.bat` | Gradle本体を別途インストールしなくてもビルド・起動できるようにするラッパースクリプト（Mac/Linux用・Windows用） |
| `gradle/wrapper/` | ラッパーが使うGradle本体（`gradle-wrapper.jar`）とバージョン指定（`gradle-wrapper.properties`） |
| `.gitignore` / `.gitattributes` | Gitで無視するファイル（ビルド成果物等）・改行コード等の設定 |
| `src/main/java/.../BackendApplication.java` | アプリの起動エントリポイント（`main`メソッド） |
| `src/main/java/.../ClockConfig.java` | アプリ全体で使う「壁の時計」（日本時間 Asia/Tokyo の `Clock`）。「今日」や「今」は `LocalDate.now(clock)` のようにこの時計で決める。AWS のサーバー（世界標準時）でも、日本の日付になる（イシュー #55） |
| `src/main/java/.../column/BoardColumn.java` | 列1つを表すエンティティ（DBの`board_columns`テーブルに対応）。名前・並び順・基本の列の印（fixed）・完了の列の印（done）・版の番号（version。`@Version` で、名前・並び順が変わって保存されるたびに JPA が 1 上げる。イシュー #71）。2つの印は作ったあとで変えない |
| `src/main/java/.../column/BoardColumnRepository.java` | 列のDB操作。左から順の一覧、右端・左端の列、完了の列（`findByDoneTrue`）を取る。並べるときは sortOrder のあとに id も並びの決まりに入れ、並び順の数字が同じ列も毎回同じ並びにする（イシュー #69） |
| `src/main/java/.../column/BoardColumnService.java` | 列の業務処理（作る＝右端に足す、名前を変える、並べ替え、消す）。作るときは番号札（`Idempotency-Key`）を RequestTokens で確かめ、同じ札なら1回目の列を返す。基本の列（やるべきこと・進行中・終わったこと）・タスクが入っている列は消せない（409。確かめてから消すまでの間にほかの端末がタスクを足し、DB の外部キーに止められたときも 409 にする）。もうない列の削除は何もしない（204）。完了の列は「終わったこと」に決まっていて、付け替えはしない。名前の変更・並べ替え・削除では、送られた版（version・versions）を今の版と比べ、ちがえば VersionConflictException（409）を投げる（削除は、基本の列・タスク入りの確かめより先。並べ替えは、ID がそろっているかの400より後。イシュー #71） |
| `src/main/java/.../column/BoardColumnController.java` | 列の REST API（`/api/columns`配下）。列を作るときはヘッダー `Idempotency-Key` を読み、`RequestTokens.parseKey` で UUID にする（形がおかしければ400）。削除の `?version=`（省略可）を読み、並べ替えの `versions` の数を `VersionCounts` で確かめる（鍵をとる前）。DBの操作は BoardColumnService に任せる |
| `src/main/java/.../column/BoardColumnRequest.java` / `BoardColumnOrderRequest.java` / `BoardColumnResponse.java` | 列の API の入れ物（作る・名前を変えるときの name と version（名前の変更で見ていた版。作るときは無視）、並べ替えるときの orderedIds と versions、返事の DTO（version 入り）） |
| `src/main/java/.../column/ColumnNotFoundException.java` | 「その id の列が見つからない」ことを表す例外（TaskNotFoundException と同じ形）。BoardColumnService が投げ、GlobalExceptionHandler が 404 の返事にする |
| `src/main/java/.../task/Task.java` | タスク1件を表すエンティティ（DBの`tasks`テーブルに対応）。どの列にいるかは列の番号（columnId）で持ち、priority は enum で持つ。版の番号（version）は `@Version` で、中身が変わって保存されるたびに JPA が 1 上げる（書くときは `WHERE version = 読んだときの版` になり、ずれていれば例外＝DB の安全網。イシュー #71） |
| `src/main/java/.../task/TaskPriority.java` | 優先度の enum（HIGH・MEDIUM・LOW）。JSON では `@JsonValue`・`@JsonCreator` で小文字（high・medium・low）にする。決まった値以外は JSON を読む時点で断る（400） |
| `src/main/java/.../task/TaskPriorityConverter.java` | enum と DB の文字の変換係（JPA の AttributeConverter）。DB には小文字で保存する（JPA 標準の `@Enumerated` だと大文字で保存され、今のデータと合わないため） |
| `src/main/java/.../task/TaskResponse.java` | API の返事専用の型（DTO）。エンティティ Task をそのまま返さず、`TaskResponse.from(task)` で画面に見せる項目だけに詰め替えて返す（版の番号 version も入る） |
| `src/main/java/.../task/TaskNotFoundException.java` | 「その id のタスクが見つからない」ことを表す例外。Controller が投げ、GlobalExceptionHandler が 404 の返事にする |
| `src/main/java/.../error/GlobalExceptionHandler.java` | グローバル例外ハンドラー（`@RestControllerAdvice`）。アプリのどこで起きたエラーも1か所で受け止め、ProblemDetail の形で返す（下の「エラーの返事」を参照）。版のずれ（VersionConflictException）・DB の安全網（`@Version` の `OptimisticLockingFailureException`）は409と `code: "VERSION_CONFLICT"`（前者は今の状態 `current` も）、ボードの番号のちがい（BoardChangedException）は409と `code: "BOARD_CHANGED"` にする（イシュー #71） |
| `src/main/java/.../version/VersionConflictException.java` | 「画面が見ていた版が、今の版とちがう」ことを表す例外（イシュー #71。[同時編集の設計書](../docs/同時編集の設計書.md) の4節）。detail（設計書 4.2節の文）と、今の状態（`current`。TaskResponse か BoardColumnResponse。並べ替えでは null）を持つ。`check(見ていた版, 今の版, …)` は、見ていた版が null（省略）なら何もせず、ちがえば投げる。Service が書き込みの鍵をとったあとに呼ぶ |
| `src/main/java/.../version/VersionCounts.java` | 並べ替え（タスクの reorder・列の order）の `versions` の数が `orderedIds` とちがえば400にする部品。Controller が鍵をとる前に呼ぶ |
| `src/main/java/.../board/BoardIds.java` | ボードの番号（表 `board_meta` の `board_id`）を DB から読む係。DB の作り直し・テストデータの投入で変わるので、覚えずに毎回読む |
| `src/main/java/.../board/BoardIdInterceptor.java` | ボードの番号の係（`HandlerInterceptor`。設計書の5節）。Controller より前（JSON を読む・入力チェックより前）に動き、`/api/` の返事すべてにヘッダー `Board-Id` を付ける。書き込み（POST・PUT・PATCH・DELETE）に `Board-Id` が付いていれば、UUID の形でなければ400、今の番号とちがえば BoardChangedException（409）。付いていない・読み取り（GET）は確かめない |
| `src/main/java/.../board/BoardIdGuard.java` | ボードの番号の2回目の確かめ（`AfterLockCheck`）。書き込みの鍵をとった直後に、同じ接続で今の番号を読み、BoardIdInterceptor が覚えた「送られた番号」とちがえば BoardChangedException（409）。1回目を通ったあと、鍵を待つ間にテストデータの投入が終わっても、番号が同じ別のカードを書き換えないため |
| `src/main/java/.../board/BoardIdResponseAdvice.java` | 返事のヘッダー `Board-Id` を確かめ直す係（`ResponseBodyAdvice`）。中身のある返事を書く直前（データを読んだあと）に番号を読み直し、BoardIdInterceptor が Controller の前に読んだ番号（リクエストに覚えたもの）と比べる。同じならそのまま、ちがえば（返事を作る間に投入がコミットされた）、データがどちらの DB のものか分からないので、どの本物の番号とも一致しない値（新しいランダムな UUID）を付ける（画面は黄色の帯を出す）。読み直せなかったときも同じ。中身のない返事（204）は確かめ直さない |
| `src/main/java/.../write/AfterLockCheck.java` | 書き込みの鍵をとった直後に、同じ接続で行う確かめの入口（WriteLockTransactionManager が呼ぶ。今は BoardIdGuard だけ） |
| `src/main/java/.../board/BoardIdConfig.java` | BoardIdInterceptor を `/api/**` に付ける設定（`WebMvcConfigurer`）。ヘルスチェック `/api/health` は外す |
| `src/main/java/.../board/BoardChangedException.java` | 「ボードの番号がちがう＝DB が作り直された」ことを表す例外。GlobalExceptionHandler が409（`BOARD_CHANGED`）の返事にする |
| `src/main/java/.../idempotency/RequestTokens.java` | 番号札（ヘッダー `Idempotency-Key`）の係（イシュー #69。[二重送信の設計書](../docs/二重送信の設計書.md) の2節）。札を UUID にする（`parseKey`。形がおかしければ400）、中身の指紋（SHA-256）を作る、表 `request_tokens` に札を入れてみる（`claim`。`INSERT … ON CONFLICT DO NOTHING`。同じ札・同じ指紋なら1回目に作ったものの番号を返し、ちがう指紋なら409、作ったものの番号がまだ入っていなければ503）、作ったものの番号を書く（`complete`）、24時間をこえた札を消す（`deleteExpired`）。追加と同じトランザクションの中で動く |
| `src/main/java/.../write/WriteLockTransactionManager.java` | 書き込みを1つずつ順番に処理するトランザクションの係（イシュー #69。設計書の4節）。標準の JpaTransactionManager に、書き込みのトランザクション（`readOnly` でないもの）を始めるとき最初に `pg_advisory_xact_lock`（アプリ全体で1つの鍵）をとる処理を足したもの。`@Transactional` の書き込みメソッド全部に通るので、呼び忘れがない。鍵はトランザクションの終わりに DB が自動で外す。鍵を待つのは上限（`app.write-lock.timeout`、そのトランザクションだけの `lock_timeout`）までで、こえたら（SQLSTATE `55P03`）WriteLockTimeoutException を投げる。鍵をとった直後に、AfterLockCheck（BoardIdGuard）で確かめ、だめならその例外（409）をそのまま投げる（イシュー #71） |
| `src/main/java/.../write/WriteLockConfig.java` | アプリの `@Transactional` が使うトランザクションの係を WriteLockTransactionManager にする設定（Spring Boot 標準の係の代わりに作る）。鍵を待つ上限を `app.write-lock.timeout` から、鍵のあとの確かめ（AfterLockCheck の部品。なければ何もしない）を渡す |
| `src/main/java/.../write/WriteLockTimeoutException.java` | 「書き込みの鍵を上限の時間までに取れなかった」ことを表す例外。GlobalExceptionHandler が 503 の返事にする |
| `src/main/java/.../task/TaskRepository.java` | DBへのCRUD操作を行うインターフェース（Spring Data JPA）。`JpaSpecificationExecutor` も受け継ぎ、条件の部品（Specification）を渡して `findAll(条件, 並び順)` で取ってこられる。並べるときは sortOrder のあとに id も並びの決まりに入れる（イシュー #69）。`renumber` は、ドラッグで番号のすき間がなくなったときに、列を 0, 1, 2… と振り直す一括の UPDATE（`ROW_NUMBER()`）。版（version）に触らないので、振り直しではほかのカードの版が上がらない（イシュー #71） |
| `src/main/java/.../task/TaskSpecifications.java` | 一覧の絞り込みの「条件の部品」（Specification）を作る。`textContains`（キーワード。LIKE の `%`・`_` はただの文字として探す）、`priorityIn`（優先度のどれか）、`dueMatches`（期限切れ／7日以内／期限なし）。条件が選ばれていないときは `Specification.unrestricted()`（条件なし）を返す |
| `src/main/java/.../task/DueFilter.java` | 期限の絞り込みの種類の enum（OVERDUE・WEEK・NONE）。URL では小文字（overdue・week・none）。作りは TaskPriority と同じ |
| `src/main/java/.../task/QueryParamConverters.java` | URL の `?priority=high`・`?due=overdue` の小文字を、TaskPriority・DueFilter に変える方法を Spring に登録する（`WebMvcConfigurer` の `addFormatters`）。決まった値以外なら 400 になる |
| `src/main/java/.../task/TaskController.java` | REST APIのエンドポイント定義（`/api/tasks`配下）。リクエストを受け取り、`@Valid` で入力をチェックし、レスポンスを返す。返事は TaskResponse（DTO）に変換してから返す。タスクが見つからないときは TaskNotFoundException を投げる（エラーの返事は自分で作らない）。タスクを作るときはヘッダー `Idempotency-Key` を読み、`RequestTokens.parseKey` で UUID にする（形がおかしければ400）。削除の `?version=`（省略可）を読み、reorder の `versions` の数を `VersionCounts` で確かめる。reorder の返事は200と、並べ直したタスクの一覧（イシュー #71）。DBの操作はすべて TaskService に任せる（Repository は直接使わない） |
| `src/main/java/.../task/TaskService.java` | 業務処理を行うService層（キーワード・優先度・期限の条件の部品を `Specification.allOf` でまとめ（AND）、列→並び順の順で取ってくる、タスク作成時に既定値（一番左の列・medium）と並び順を決める、列が変わったタスクを移動先の一番下に置くなど。一番下の並び順は、削除で番号に隙間があっても重ならないよう「列の最大値＋1」で決める。送られてきた列の番号が本当にあるかを確かめる（`requireColumn`、なければ400））。読み取り・作成・更新（PUT／PATCH）・削除・並び替え・書き出し・読み込みを担当。書き出しは `REPEATABLE_READ` で、1つの状態を最後まで読む。作成では番号札（`Idempotency-Key`）を RequestTokens で確かめ、同じ札なら1回目のタスクを返す（1回目のタスクが消されていれば404）。もうないタスクの削除は何もしない（204）。更新（PUT／PATCH）・move・reorder・削除では、送られた版を今の版と比べ、ちがえば VersionConflictException（409）を投げる（確かめる順番は、ある → 版 → そのほかの決まり。reorder は1枚でもずれたらどれも動かさない。イシュー #71）。move で番号のすき間がなくなったら、`TaskRepository.renumber`（版に触らない一括の UPDATE）で振り直し、動かすカードと上のカードを DB から読み直してから番号を決める。reorder は並べ直したタスクを返す。`@Transactional` で、メソッドごとのDB操作を「全部成功か、全部取り消し」にする（読み取りは `readOnly`。書き込みは WriteLockTransactionManager の鍵で1つずつ動く） |
| `src/main/java/.../task/TaskRequest.java` | タスク作成・更新時のリクエストボディの型（text は空欄不可・255文字まで、columnId は列の番号（省略可）、priority は enum なので決められた値のみ。version は更新（PUT）で見ていた版（省略可。作るときは無視）） |
| `src/main/java/.../task/TaskPatchRequest.java` | 一部だけ更新（PATCH）するときのリクエストボディの型（すべて省略可。送るなら text は空白だけ不可・255文字まで、columnId は列の番号、priority は enum なので決められた値のみ。version は見ていた版） |
| `src/main/java/.../task/ReorderRequest.java` | 並び替えAPIのリクエストボディの型（columnId と orderedIds は必須。versions は orderedIds と同じ数・同じ順の版で、省略可） |
| `src/main/java/.../task/MoveRequest.java` | カード1枚を動かすAPI（move）のリクエストボディの型（columnId は必須。prevId＝すぐ上に入れるカードの ID。省略すると列の一番上。version は動かすカードの見ていた版で、省略可） |

| `src/main/java/.../task/TaskFileItem.java` | ファイル（version 2）に入れるタスク1件の型（text・priority・dueDate。id・列・並び順はなし）。`from(Task)` で DB のタスクから作る |

## 静的解析（PMD）

PMD は、Java のコードから「バグになりやすい書き方」を見つける道具。規則は PMD が用意している `quickstart` を使う（`build.gradle` の `pmd { }`）。

| 実行場所 | コマンド | 説明 |
| --- | --- | --- |
| `backend`フォルダ | `./gradlew pmdMain pmdTest` | 本体とテストのコードをチェックする。1件でも見つかると失敗し、場所と規則名が表示される（`./gradlew check` にも含まれる） |

- 見つかったものは、基本は直す。PMD の指摘が Spring の書き方と合わない（的外れな）ときだけ、その場所に `@SuppressWarnings("PMD.規則名")` を付けて止め、止めた理由をコメントに書く（例：[BackendApplication.java](src/main/java/com/taskmanagement/backend/BackendApplication.java) の `UseUtilityClass`）
- 止める範囲はなるべく狭くする（プロジェクト全体で止めると、ほかの場所の本当の問題も見逃すため）
- GitHub Actions（`taskmanagement/.github/workflows/ci.yml`）でも、PR ごとに `./gradlew check` が自動で動く

## 書き方のチェック（Checkstyle）

Checkstyle は、コードの「書き方がそろっているか」を見る道具（PMD は「バグになりやすい書き方」を見る）。決まりは `config/checkstyle/checkstyle.xml` に書いてあり、今のコードに合う基本的なものだけを選んでいる。

| 実行場所 | コマンド | 説明 |
| --- | --- | --- |
| `backend`フォルダ | `./gradlew checkstyleMain checkstyleTest` | 本体とテストのコードをチェックする。1件でも見つかると失敗し、ファイル名・行番号・規則名が表示される（`./gradlew check` にも含まれる） |

| 決まり | 内容 |
| --- | --- |
| FileTabCharacter | インデントにタブ文字を使わない（スペース4つ） |
| NewlineAtEndOfFile | ファイルの最後は改行で終える |
| LineLength | 1行は120文字まで |
| AvoidStarImport・UnusedImports・RedundantImport | `import ...*;` を使わない。使っていない・重なっている import を残さない |
| 名前の付け方（TypeName・MethodName・ConstantName など） | クラスは `TaskService`、変数やメソッドは `taskService`、定数は `LOG` の形 |
| NeedBraces | `if`・`for` などは、1行でも `{ }` で囲む |
| そのほか | 1行に1つの文だけ（OneStatementPerLine）、空の catch を書かない（EmptyCatchBlock）、記号の前後に空白（WhitespaceAround）など |

## 自動テスト

テストは JUnit Jupiter で書き、DB は Testcontainers が Docker で用意する使い捨ての PostgreSQL を使う。開発用の DB（docker compose の 5432）は使わないので、起動していなくてもテストが動き、開発用のデータも汚さない（Docker Desktop は起動しておく）。

| 実行場所 | コマンド | 説明 |
| --- | --- | --- |
| `backend`フォルダ | `./gradlew test` | テストだけを動かす。結果は `build/reports/tests/test/index.html` で見られる |
| `backend`フォルダ | `./gradlew check` | コンパイル・PMD・Checkstyle・テストをまとめて動かす（GitHub Actions と同じ） |

`TaskApiTest` で確かめていること：

| 場面 | 確かめること |
| --- | --- |
| 登録 | columnId・priority を省略すると一番左の列・medium になり、JSON は小文字で返る |
| 削除のあとの登録 | 削除で並び順に隙間ができても、新しいタスクは「列の最大値＋1」に入る（以前あった、番号が重なる不具合の再発防止） |
| 完了ボタン | PATCH で完了の列の番号を送ると、完了の列の一番下に移る |
| 並び替え（move・reorder） | move は上のカードと DB で本当にすぐ下のカードの真ん中に入る（すき間がなければ振り直す）。reorder は送ったカードどうしで席を入れ替え、送らなかったカードは動かさない。返事は 200 で、並べ直したカードを送った順に返す。別の列のカードが混じると 400 |
| 削除 | 204 が返り、そのあと取得すると 404 になる |
| 絞り込み（優先度） | priority を2つ書くと、そのどちらかの優先度のタスクだけが返る |
| 絞り込み（期限） | overdue・week・none が、それぞれ正しいタスクだけを返す。境目（今日は期限切れに入らない、今日＋6日は7日以内に入り、＋7日は入らない）も確かめる。期限日は `LocalDate.now()` から作るので、いつ動かしても同じ結果になる |
| 絞り込み（組み合わせ） | keyword と priority を一緒に書くと、両方を満たすタスクだけが返る（片方だけ合うタスクも用意して、OR になっていないことを確かめる） |
| キーワードの `%` | `100%` で検索しても、`%` を「何でもよい文字」として扱わない |
| 入力ミス | タスク名が空・256 文字、並び替えで columnId がない → 400 と理由（`errors`）。ない列の番号 → 400 と理由（`detail`）。DB には何も保存されない。絞り込みの priority・due が決まっていない値 → 400 |
| 見つからない | 存在しない id を書き換える → 404 と理由（`detail`） |
| 書き出し・読み込み | 書き出しは version 2 の列ごとの形で、id なし。読み込むと列もタスクもファイルどおりに置き換わる。version 1 のファイルも3列に入れて読める。おかしいタスクがある・基本の列がちょうど3つでない・完了の列がちょうど1つでない・完了の列が基本の列でない・知らない version → 400 で何も変えない。書き出したファイルを読み込むと、足した列も含めて元に戻る |

`BoardColumnApiTest` で確かめていること：

| 場面 | 確かめること |
| --- | --- |
| 一覧・作る | 左から順に返る。作った列は名前の前後の空白が取れ、完了の印なしで右端に入る。名前が空なら 400 |
| 名前を変える | 名前が変わる。ない列なら 404 |
| 完了の列 | 付け替えの URL（`PUT /api/columns/{id}/done`）はなく、完了の列は「終わったこと」のまま |
| 並べ替え | 送った順に左から並ぶ。足りない・重なっている ID なら 400 で並びは変わらない |
| 消す | 足した空の列は 204。タスクが入っている列・基本の3列は 409 で残る。ほかの画面ですでに消された列は 204 で、ほかの列は変わらない |

`DoubleSubmitTaskApiTest`・`DoubleSubmitColumnApiTest`・`DoubleSubmitConcurrencyTest`・`WriteLockTimeoutTest` で確かめていることは、[二重送信の設計書](../docs/二重送信の設計書.md) の 5.1節の表（DS-01〜34）のとおり。

`concurrentedit/` のテスト（`ConcurrentEdit*Test` の 9 ファイル。44件）で確かめていることは、[同時編集の設計書](../docs/同時編集の設計書.md) の 7.1節の表（CE-01〜49 と CE-45b・CE-45c・CE-47b。版の付き方・版のずれ・確かめる順番・同時に送る・ボードの番号・V6 の移行）のとおり。期待値は設計書だけから決めている。

- テストごとに（`@BeforeEach`）タスクと列を全部消し、「やるべきこと／進行中／終わったこと」の3列を作り直してから始める。前のテストのデータが混ざると、結果がテストの順番で変わってしまうため

## 起動手順（DB + バックエンド）

PostgreSQLはインストール不要で、Dockerコンテナとして起動する（設定ファイルは`taskmanagement/docker-compose.yml`）。

| 順番 | 実行場所 | コマンド | 説明 |
| --- | --- | --- | --- |
| 1 | `taskmanagement`フォルダ | `docker compose up -d` | PostgreSQLをDockerで起動 |
| 2 | `backend`フォルダ | `./gradlew bootRun` | バックエンド（Java）を起動（起動時に Flyway が`board_columns`・`tasks`・`request_tokens`・`board_meta`テーブルを作る・直す） |
| 3（任意） | `taskmanagement`フォルダ | `docker compose exec -T postgres psql -U postgres -d taskdb < db/seed-test-data.sql` | テストデータ（3列とタスク10件）を投入（既存の列とタスクと、二重送信を防ぐ番号札〔`request_tokens`〕はすべて消えて入れ直される。番号を振り直すので、古い札が別のものを指さないよう、札も消す。ボードの番号〔`board_meta` の `board_id`〕も新しくなるので、投入の前から開いている画面は、書き込みが409で止まり、黄色の帯「読み込み直す」が出る〔番号が同じ別のカードを書き換えないため。イシュー #71〕。投入は全体を1つのトランザクションにし、アプリの書き込みと同じ鍵をとるので、アプリの書き込みとは重ならない。書き出し（export）とのデッドロックを防ぐため、表を書き出しが読む順にまとめてつかむ。エラーが出たらそこで止まる〔`ON_ERROR_STOP`〕。バックエンドを一度起動して V6 を当ててから流す〔`board_meta` がないと止まり、何も変わらない〕） |

DBを止めるときは`taskmanagement`フォルダで`docker compose down`を実行する（`docker compose down -v`にするとデータも消えるので注意）。

| PUT | /api/tasks/{id}/move | ドラッグ用。タスク1件を、指定した列の prevId のタスクのすぐ下（prevId を省くと一番上）に移す。番号は、上のタスクと DB で本当にすぐ下のタスクの真ん中（すき間がなければ列を 0, 1, 2… と振り直す。振り直しでは、ほかのタスクの版は上がらない）。成功時は200（動かしたあとのタスク）、タスクがなければ404、prevId が別の列なら400。版つき（`{"columnId": 2, "prevId": 7, "version": 3}`。動かすタスクの版だけを比べ、古ければ409・`current` つき。prevId の確かめより先） |
| PUT | /api/tasks/reorder | 自動並び替え用。指定した列の中で、送った ID のタスクどうしの番号（席）を入れ替え、送った順に並べる。送らなかったタスクの番号は変えない。成功時は**200**と、並べ直したタスク（新しい sortOrder・version 入り。もう消えていたものは入らない）を送った順に並べた配列（前は204だった）。入力が不正・別の列のタスクが混じっていれば400。版つき（`"versions": [0, 2, 1]`。数がちがえば400、1枚でも古ければ、どのタスクも動かさずに409（`current` なし）。別の列のタスクの400より先） |
| GET | /api/tasks/export | 書き出し。全部の列とタスクを TaskFile（version 2）の JSON で返し、`Content-Disposition: attachment; filename="tasks-日付.json"` を付ける。成功時は200。最初に DB に聞いたときの1つの状態を最後まで読む（`REPEATABLE_READ`）ので、読み込み（import）と重なっても、前か後のどちらかの状態のファイルになる（読み取りだけなので、書き込みの鍵は待たない） |
| POST | /api/tasks/import | 読み込み。全部の列とタスクを消して、送られた TaskFile の列とタスクに置き換える（1つのトランザクション。並び順はファイルに書いた順に 0, 1, 2… と振り直す）。version 1 のファイルは3列（やるべきこと／進行中／終わったこと）に入れる。成功時は204、入力が不正・完了の列がちょうど1つでない・version が 1・2 でない・JSON が読めなければ400（何も変えない）。版では止めない（新しい列・タスクの版は0）。`Board-Id` は確かめる |

## エラーの返事（ProblemDetail）

エラーの返事は、どの API でも ProblemDetail（RFC 9457。Spring 標準のエラーの形）にそろえている。Content-Type は `application/problem+json`。作っているのは [GlobalExceptionHandler.java](src/main/java/com/taskmanagement/backend/error/GlobalExceptionHandler.java) の1か所だけ。

```json
{"type":"about:blank","title":"Bad Request","status":400,
 "detail":"入力内容に誤りがあります","instance":"/api/tasks",
 "errors":{"text":"タスク名を入力してください"}}
```

| 場面 | status | detail | その他 |
| --- | --- | --- | --- |
| 入力チェック違反（`@Valid`。text が空・256文字以上、並び替えの columnId なし など） | 400 | 入力内容に誤りがあります | `errors` に「項目名 → 理由」（例：`orderedIds[1]` は orderedIds の2番目） |
| JSON が読めない（形が崩れている、priority に決まっていない値、columnId が数字でない） | 400 | JSON の形と、項目の値（列の番号は数字、優先度は high・medium・low）を確かめるよう案内する文（壊れたファイルの読み込みにも合う言い方） | — |
| ない列の番号・別の列のカード・おかしなファイルなど（Service の `ResponseStatusException`） | 400 | 理由の文（例：id が ○ の列はありません） | — |
| タスクが見つからない（TaskNotFoundException） | 404 | id が ○ のタスクは見つかりません | — |
| 列が見つからない（ColumnNotFoundException） | 404 | id が ○ の列は見つかりません | — |
| 基本の列・タスクが入っている列を消そうとした | 409 | 消せない理由と、どうすればよいかの文 | `code` は付かない（画面が版のずれと見分けるため） |
| 番号札（`Idempotency-Key`）が UUID の形でない（RequestTokens の `ResponseStatusException`） | 400 | 番号札は UUID の形で送るよう案内する文 | — |
| 同じ番号札で、ちがう内容が送られた（RequestTokens の `ResponseStatusException`） | 409 | 同じ番号札で、ちがう内容が送られました（新しい内容なら新しい札で送るよう案内） | — |
| 同じ番号札で1回目に作ったタスク・列が、もう消されている（Service の `ResponseStatusException`） | 404 | この番号札で作ったタスク（列）は、すでに消されています | 作り直さない |
| 札の行はあるのに、作ったものの番号がまだ入っていない（RequestTokens の `ResponseStatusException`。書き込みの鍵があるので、ふだんは起きない） | 503 | 同じ番号札の追加が、まだ終わっていません。少し待ってから、もう一度お試しください | 409 にしない（画面が札を取り替えて2件できてしまうため）。画面は同じ札のまま送り直す |
| id が数字でない・存在しない URL など（Spring の決まった例外） | 400・404 など | Spring が作る英語の文 | 親クラス（ResponseEntityExceptionHandler）が作る |
| 版の配列（`versions`）の数が、並べる順番（`orderedIds`）とちがう（VersionCounts の `ResponseStatusException`） | 400 | 並べる順番（orderedIds）と版（versions）の数をそろえてください | 何も変えない |
| ボードの番号（ヘッダー `Board-Id`）が UUID の形でない（BoardIdInterceptor の `ResponseStatusException`） | 400 | ボードの番号（Board-Id）は UUID の形で送ってください | 何も書き込まない |
| 画面が見ていた版が、今の版とちがう（VersionConflictException） | 409 | 操作ごとの文（例：ほかの画面で、このタスクが変更されています。最新の内容を確かめてから、もう一度操作してください。[同時編集の設計書](../docs/同時編集の設計書.md) 4.2節の表） | `code: "VERSION_CONFLICT"`。1つのものが対象の操作（タスクの PUT・PATCH・move・DELETE、列の PUT・DELETE）では `current`（そのタスク・列の今の状態。返事の型と同じ形）。並べ替えには付かない。何も書き込まない |
| DB の安全網（JPA の `@Version` が書くときに版のずれに気づいた。`OptimisticLockingFailureException`。書き込みの鍵があるので、ふだんは起きない） | 409 | ほかの画面で変更されています。最新の状態を読み込んでから、もう一度操作してください | `code: "VERSION_CONFLICT"`、`current` なし。サーバーのログにも残す |
| ボードの番号がちがう＝DB が作り直された（BoardChangedException） | 409 | データベースが作り直されています。画面を読み込み直してください | `code: "BOARD_CHANGED"`。何も書き込まない |
| 書き込みの鍵を、上限（`app.write-lock.timeout`）までに取れなかった（WriteLockTimeoutException） | 503 | いま別の書き込みが続いています。少し待ってから、もう一度お試しください | 何も書き込んでいないので、そのまま送り直してよい。サーバーのログにも残す |
| 上のどれでもない思いがけないエラー | 500 | サーバーでエラーが起きました | 例外の中身は返さず、サーバーのログにだけ出す |
