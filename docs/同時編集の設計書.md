# 同時編集の設計書（イシュー #71）

2 つの端末（タブ）で同じカードや列を変えたとき、**あとから保存したほうが、先の変更を黙って上書きしない**ようにするための決まりと、確かめる場面の一覧（要件定義書 No.24）。

直す前は「後勝ち」でした。たとえば、タブ B でカードの名前を「牛乳を買う（2 本）」に直したあと、開いたままの古いタブ A で同じカードの優先度だけ変えて保存すると、A が覚えていた古い名前「牛乳を買う」で上書きされ、B で直した名前は**知らせなしに消えていました**。「まれでも直す」の決まり（入力したものが黙って消える）に当たるので直しました（イシュー #71 で実装済み。いまは A の保存が止まり、いまの内容が見えます）。

たとえ：共有のホワイトボードを、朝にスマホで写真に撮ったとします。夕方、その写真を見ながら「ここを書き直して」と頼むと、昼にだれかが書き足した分を知らずに消してしまいます。#69 の「書き込みの鍵」（レジが 1 つ）は、**同じ瞬間**に 2 人が書くのは防げますが、**古い写真を見ながら頼む**ことは防げません。そこで、ボードの各カードに「第何版か」の印を付け、「わたしが見ていたのは第 3 版です」と一緒に頼んでもらいます。今が第 4 版なら、だれかが先に直しているので、書き込まずに知らせます。

この印を **版（version）** と呼びます。書き出しのファイルの `version`（ファイルの形の版。今は 2）とは**別のもの**です。

### 1.3 上書きしないもの・すでに守られているもの

| 操作・場面 | 理由 |
| --- | --- |
| タスク・列の追加（`POST`） | 新しく作るだけで、ほかを書き換えない。2 回届いても 1 件（番号札。#69）。消された列への追加は 400 で止まり、入力も残る |
| 書き出し（export） | 読むだけ。import と重なっても混ざらない（#69 の `REPEATABLE_READ`） |
| 読み込み（import） | 「今の列とタスクを全部消して、ファイルに置き換える」ことが目的で、確認のダイアログでもそう伝えている。ほかの画面での変更も置き換わるのは、利用者が選んだとおり。**版では止めない**（4.5 を参照） |
| 同じ瞬間の 2 本の書き込み | 書き込みの鍵（#69。`pg_advisory_xact_lock`）で 1 つずつ順番に動く |
| 2 回目の削除・もうないものの削除 | 204（#69） |
| タスクが入っている列・基本の列の削除 | 409（#38） |
| 編集でカードが元の列に戻る | 編集では列を送らない（#20） |

## 2. 方式を比べる

| 方式 | どう動くか | 良い点 | 困る点 | 判定 |
| --- | --- | --- | --- | --- |
| **① 版の番号（`version` 列）＝楽観的ロック** | 行ごとに整数の版を持ち、変えるたびに 1 上げる。画面は「見ていた版」を一緒に送り、今の版とちがえば 409 で止める | 整数を比べるだけなので確実。Java（JPA）の標準の仕組み `@Version` がある（学ぶ価値がある）。テストが書きやすい。#69 の番号札と同じく「送らなければ今までどおり」にできる。No.14②（自動の反映）でも「版の大きいほうが新しい」と使える | DB に列を足す（Flyway の V6）。1 行に 1 つの版なので、関係ない項目の変更（並びだけ変わった、など）でも止まる（6.2 の「この入力で上書き保存」で 1 回押し直せば済む） | **おすすめ** |
| ② 更新日時（`updated_at`）で比べる | 変えた日時を持ち、画面が見ていた日時と比べる | 「いつ変わったか」も分かる | PostgreSQL はマイクロ秒、ブラウザの `Date` はミリ秒なので、行き来で丸まってずれる。同じ時刻に 2 回変わると見分けられない。サーバーの時計が戻ると狂う。比べるだけなら①の整数のほうが確実 | 選ばない |
| ③ 全体の書き込みの鍵の中で、最後に読んだ状態と比べる | 鍵（#69）の中で読み直してから書く | 新しい列が要らない | 鍵が守るのは「同時の一瞬」だけ。画面が古いまま何分もたつ間は守れない。サーバーは、画面がいつ何を見たかを知らないので、画面から何かを送ってもらう必要がある（それが①か⑤）。**鍵は、①の「比べてから書く」を割り込みなしにするために使う**（4.5） | 単独では選ばない |
| ④ 後勝ちのまま | 何もしない | 作業がない | 入力したものが黙って消える。「まれでも直す」の決まりに反する | 選ばない |
| ⑤ 画面が見ていた値を送り、今の値と比べる | 編集なら「見ていた名前・優先度・期限」、○ なら「見ていた列」を送り、今とちがえば止める | DB の移行が要らない。関係ない項目の変更では止まらない | 操作ごとに送る項目がちがい、決まりとテストが複雑になる。並び順（小数）の比べ合わせは、番号の振り直しでまちがって止まる。並べ替え・削除では送る量が多い | 選ばない |
| ⑥ HTTP の ETag と `If-Match`（ずれたら 412） | ①の版を、HTTP の決まったヘッダーで送る | HTTP の標準の形 | 並べ替え（何枚ものカード）を 1 つのヘッダーで表せない。止まったときが 409（ほかの理由）と 412 に分かれ、画面の扱いが増える。考え方は①と同じなので、①を本文（JSON）で送る形にする | 選ばない（①に含める） |
| ⑦ 編集中は鍵をかける（悲観的ロック） | ✎ を開いたら、ほかの画面は編集できない | ぶつかる前に分かる | 開いたまま閉じたタブ・スリープした PC が鍵を持ち続ける。鍵の期限・解き方の仕組みが要る。1 人で使うアプリには重い | 選ばない |
| ⑧ 項目ごとに自動でまとめる（マージ） | 名前と優先度のように、ちがう項目の変更なら両方残す | 止まる回数が減る | 項目ごとの履歴が要り、作りが大きい。①で止めて入力を残せば、データは失われない | 後回し（8 節） |

**選んだ理由**：①は、整数を 1 つ比べるだけで「古い画面からの書き込み」を確実に見分けられ、Java の標準の部品で作れて、テストも書きやすい。止まったときも、入力を残して最新の内容を見せれば、利用者が 1 回押し直すだけで済む。#69 の番号札・書き込みの鍵とも、そのまま組み合わせられる（4.5）。

**選ばなかった理由**は表の「困る点」のとおり。②は①より不確か、③は単独では守れない、④は決まりに反する、⑤は複雑でまちがって止まる、⑥は①と同じ考えで扱いが増える、⑦は 1 人のアプリに重い、⑧は大きいので後回し。

## 3. 版の付き方

### 3.1 データベース（Flyway の V6）

- 新しいファイル `V6__add_version_and_board_id.sql`（V1〜V5 は書き換えない）。
- `tasks` と `board_columns` に、`version BIGINT NOT NULL DEFAULT 0` を足す。**今ある行は 0 から始まる**（`DEFAULT` つきの列の追加なので、PostgreSQL 11 より新しい版では、表を書き直さずにすぐ終わる）。
- `DEFAULT 0` は残す：テストデータの投入（`db/seed-test-data.sql`）のように、SQL で直接入れる行も 0 になる。
- あわせて、5 節の「ボードの番号」の表 `board_meta` も作る。

### 3.2 版が上がるとき・上がらないとき

- **行の中身（保存している項目）が 1 つでも変わったら、ちょうど 1 上がる**。何も変わらなかったら（同じ名前・同じ列への PATCH など）、上がらない。
  - タスク：`text`・`column_id`・`priority`・`due_date`・`sort_order` のどれか。
  - 列：`name`・`sort_order`（`is_fixed`・`is_done` は変えない）。
- 作ったとき（追加・import）は 0。
- **例外：ドラッグのときの「番号の振り直し」（すき間がなくなったとき、列を 0, 1, 2… にする）では、版を上げない**。見た目の順番は変わらないので、ほかの画面が古い番号を持っていても困らない（サーバーは画面の番号を信じず、いつも DB の番号で決める）。上げると、画面は振り直しがあったことを知らないので、同じ画面の次の操作がまちがって止まる（1.2 の #14 と同じ形）。
  - 作り方の注意：JPA の `@Version` は、行が変わると自動で版を上げる。振り直しは、版に触らない一括の `UPDATE` 文（例：`ROW_NUMBER() OVER (ORDER BY sort_order, id) - 1` で番号を決める）で行い、そのあと、持っているタスクを DB から読み直す。
- 版は、そのタスク・列だけのもの。カードを動かしても、列の版は上がらない。

### 3.3 返事に版を入れる

- タスクの返事（`TaskResponse`）と列の返事（`BoardColumnResponse`）に、`version`（数字）を足す。一覧（`GET /api/tasks`・`GET /api/columns`）、1 件（`GET /api/tasks/{id}`）、追加・更新・移動の返事、すべてに入る。
- 書き出しのファイルには入れない（ファイルの形は version 2 のまま）。

## 4. 版の送り方と、ずれたときの返事

### 4.1 送り方

**版は省略できる。省略したら、今までどおり確かめない（後勝ち）**。#69 の番号札（札なしは今までどおり）と同じ考えで、API を直接呼ぶ人・今のテスト・デプロイのときに開いたままの古い画面（版を知らない）を壊さないため。**画面は必ず送る**。`null` を書いたときも、省略と同じ。

| 操作 | 送り方 | 例 |
| --- | --- | --- |
| `PUT /api/tasks/{id}` | 本文に `version` | `{"text":"牛乳を買う","priority":"high","dueDate":null,"version":3}` |
| `PATCH /api/tasks/{id}` | 本文に `version` | `{"columnId":3,"version":3}` |
| `PUT /api/tasks/{id}/move` | 本文に `version`（動かすカードの版。`prevId` のカードの版は送らない） | `{"columnId":2,"prevId":7,"version":3}` |
| `PUT /api/tasks/reorder` | 本文に `versions`（`orderedIds` と同じ数・同じ順の版の配列。`versions[i]` が `orderedIds[i]` の版） | `{"columnId":1,"orderedIds":[9,4,6],"versions":[0,2,1]}` |
| `DELETE /api/tasks/{id}` | URL の `?version=` | `DELETE /api/tasks/5?version=3` |
| `PUT /api/columns/{id}` | 本文に `version` | `{"name":"確認待ち","version":1}` |
| `PUT /api/columns/order` | 本文に `versions`（`orderedIds` と同じ数・同じ順） | `{"orderedIds":[1,2,4,3],"versions":[0,0,1,0]}` |
| `DELETE /api/columns/{id}` | URL の `?version=` | `DELETE /api/columns/4?version=1` |
| `POST /api/tasks`・`POST /api/columns` | 送らない。**書いても無視する**（新しいものは必ず 0）。番号札の中身の指紋にも入れない | — |
| `POST /api/tasks/import` | 送らない（版では止めない） | — |

- `version`・`versions` の中が数字でない → 400（今の「JSON が読めない」の返事。`DELETE` の `?version=abc` は Spring の決まった 400）。
- `versions` の数が `orderedIds` とちがう → 400（detail「並べる順番（orderedIds）と版（versions）の数をそろえてください」）。何も変えない。
- 送った版が今の版と同じなら、ふだんどおり書いて、新しい版を返す。

### 4.2 ずれたときの返事（409）

送った版が今の版とちがう → **409**。何も書き込まない。ProblemDetail に 2 つの項目を足す。

- `code`：`"VERSION_CONFLICT"`（同じ 409 の「タスクが入っている列は消せない」「同じ番号札でちがう中身」と、画面が見分けるため）。
- `current`：そのタスク（または列）の**今の状態**（返事の型と同じ形。`version` も入る）。1 つのものを対象にする操作だけに付ける。画面は、もう 1 回取りに行かなくても最新を見せられる。

```json
{"type":"about:blank","title":"Conflict","status":409,
 "detail":"ほかの画面で、このタスクが変更されています。最新の内容を確かめてから、もう一度操作してください",
 "instance":"/api/tasks/5","code":"VERSION_CONFLICT",
 "current":{"id":5,"text":"牛乳を買う（2本）","columnId":1,"priority":"medium","dueDate":null,"sortOrder":2.0,"version":4}}
```

| 操作 | detail | `current` |
| --- | --- | --- |
| タスクの `PUT`・`PATCH`・`move`・`DELETE` | ほかの画面で、このタスクが変更されています。最新の内容を確かめてから、もう一度操作してください | あり（タスク） |
| `PUT /api/tasks/reorder` | ほかの画面で、この列のタスクが変更されています。最新の状態を読み込んでから、もう一度並び替えてください | なし |
| 列の `PUT`・`DELETE` | ほかの画面で、この列が変更されています。最新の内容を確かめてから、もう一度操作してください | あり（列） |
| `PUT /api/columns/order` | ほかの画面で、列が変更されています。最新の状態を読み込んでから、もう一度並べ替えてください | なし |
| DB の安全網（4.5。ふだんは起きない） | ほかの画面で変更されています。最新の状態を読み込んでから、もう一度操作してください | なし |

### 4.3 確かめる順番

1. ボードの番号（5 節）。ちがえば 409（`BOARD_CHANGED`）。
2. 入力チェック（`@Valid`、JSON が読める、`versions` の数）。だめなら 400。
3. 書き込みの鍵をとる（#69）。
4. 対象があるか。タスク・列がなければ、`PUT`・`PATCH`・`move` は 404、`DELETE` は 204（#69 のまま。版は見ない）。
5. **版**。ちがえば 409（`VERSION_CONFLICT`）。
6. そのほかの決まり：ない列の `columnId`（400）、`prevId` が自分自身・ない・別の列（400・404・400。今までどおり）、基本の列・タスクが入っている列の削除（409。`code` なし）、列の並べ替えで ID がそろわない（400）、reorder に別の列のカードが混じる（400）。

例外：列の並べ替え（`PUT /api/columns/order`）だけは、全部の列の ID がそろっているか（400）を版より先に見る（4.4。ID がそろっていないと、どの版をどの列と比べるかが決められないため）。

版を「そのほかの決まり」より先に見る理由：古い画面から来た頼みは、そもそも古い状態をもとにしているので、「入力がおかしい」より「ほかで変わった」と知らせるほうが正しい。たとえば、ほかの画面で別の列へ動かしたカードを reorder に入れると、そのカードの版は上がっているので、400 ではなく 409 になる。

### 4.4 操作ごとの決まり

- **ドラッグ（move）**：動かすカードの版だけを比べる。`prevId` のカードの版は比べない（「Y のすぐ下に入れて」という頼みは、Y の位置が変わっていても意味が通るため）。`prevId` のカードがほかの画面で別の列へ動いていたら、今までどおり 400、消えていたら 404（画面は 6.2 の「並び替えを保存できませんでした…」で知らせる）。列をまたぐ移動も、同じ列の中の移動も同じ扱い。
- **自動並び替え（reorder）**：送ったカード全部の版を比べ、**1 枚でもちがえば、どのカードも動かさずに 409**（一部だけ並べ替わると、並びが中途半端になるため）。送ったカードのうち、もう消えたもの（ない id）は、今までどおり飛ばし、版も見ない。同じ id が 2 回あるときは、両方の版を比べる。**返事を 204 から 200 に変え**、並べ直したタスク（消えて飛ばしたものを除く）を、`orderedIds` の順の配列で返す（新しい `sortOrder`・`version` が入る。画面が新しい版を知るため）。
- **削除**：もうないものは 204（版は見ない。#69 のまま）。あるのに版がちがえば 409（ほかで直した内容を、古い確認のまま消さない）。
- **列の削除**：版がちがえば 409（`VERSION_CONFLICT`）。版が合っていても、基本の列・タスクが入っている列は、今までどおり 409（`code` なし）。
- **列の並べ替え**：全部の列の ID がそろっているかを先に見る（400。今までどおり）。そのあと、`versions` があれば全部の版を比べる。
- **番号札の送り直し**（#69）：同じ札・同じ中身の 2 回目は、1 回目に作ったものの**今の状態**（今の `version`）を返す。作ったあとに直されていれば、直したあとの中身と版が返る。

### 4.5 ほかの仕組みとの相性

| 仕組み | どうなるか |
| --- | --- |
| 書き込みの鍵（#69） | 版を比べるのは鍵をとったあと。比べてから書くまでの間に、ほかの書き込みが割り込まない。そのため `SELECT … FOR UPDATE` などは要らない |
| JPA の `@Version` | 安全網として付ける。書くときに `UPDATE … WHERE version = 見ていた版` になり、もしずれていれば例外（`ObjectOptimisticLockingFailureException`）になる。鍵があるので、ふだんは起きない。起きたら 500 ではなく 409（`VERSION_CONFLICT`、`current` なし）にする |
| 待ちの上限（503） | 何も書いていないので、同じ版のまま送り直してよい（今までどおり） |
| 番号札（`Idempotency-Key`） | 追加には版がない。送り直しは、今の状態と版を返す（4.4） |
| 読み込み（import） | 版では止めない（全部置き換えるのが目的）。新しい列・タスクは新しい番号（id）で、版は 0。古い画面が前の番号で書き込むと、もうないので 404（`DELETE` は 204）。番号は DB の通し番号なので、import のあとも前の番号は使われない |
| 書き出し（export） | 変わらない（版はファイルに入れない） |
| 削除済みを編集した | 404（今までどおり）。版より先に「あるか」を見る（4.3） |
| 同じ人が、自分の別のタブで変えた | ほかの端末と同じに扱う（見分けない）。古い画面を見ていたことに変わりはないため |

## 5. データベースが作り直されたとき（ボードの番号）

1.2 の #13 を防ぐ。DB が作り直されると、カードの番号（id）も版も 1・0 から振り直されるので、版だけでは「別の DB のカード」だと分からない。そこで、**DB ごとに 1 つの番号（ボードの番号）**を持つ。

たとえ：ホワイトボードを新しいものに取り替えたら、ボードの裏の製造番号も変わる。古い写真に写っている製造番号とちがえば、「このボードは、もう写真のボードではない」と分かる。

- V6 で、表 `board_meta` を作る：`id SMALLINT PRIMARY KEY CHECK (id = 1)`（いつも 1 行だけ）、`board_id UUID NOT NULL`。`INSERT INTO board_meta (id, board_id) VALUES (1, gen_random_uuid())`（`gen_random_uuid()` は PostgreSQL 13 からの標準の関数。手元の Docker も RDS も 17）。
  - DB を作り直すと（RDS の作り直し・`down -v`）、Flyway が V6 を当て直すので、新しい番号になる。
  - テストデータの投入（`db/seed-test-data.sql`）は番号を振り直すので、`UPDATE board_meta SET board_id = gen_random_uuid();` も流す。
  - import では変えない（import のあとは前の番号を使わないので、要らない）。
- サーバーは、**`/api/` のすべての返事**（エラーも。`/api/health` は除いてよい）に、ヘッダー `Board-Id: <UUID>` を付ける。
- 画面は、最初に受け取った `Board-Id` を覚え、**書き込み（`POST`・`PUT`・`PATCH`・`DELETE`）のたびに、ヘッダー `Board-Id` で送る**。
- サーバーは、書き込みに `Board-Id` があれば、今の番号と比べる。
  - 同じ → ふだんどおり。
  - ちがう → **409**、`code: "BOARD_CHANGED"`、detail「データベースが作り直されています。画面を読み込み直してください」。何も書き込まない。**ほかのどの確かめよりも先**（入力がおかしくても、もうない番号の削除でも、409）。
  - UUID の形でない → 400（detail「ボードの番号（Board-Id）は UUID の形で送ってください」）。
  - ない → ふだんどおり（古い画面・API を直接呼ぶ人のため。版と同じ考え）。
- 読み取り（`GET`）は確かめない（読むだけなので困らない）。代わりに、画面が返事の `Board-Id` と覚えた番号を比べる（6.1）。
- 確かめる場所は 2 か所（実装で直した。最初は「Controller より前の 1 か所でよい」としていた）。
  - 1 回目：Controller より前（`HandlerInterceptor`。`board/BoardIdInterceptor`）。上の「ほかのどの確かめよりも先」を守るため。返事のヘッダー `Board-Id` もここで付ける。
  - 2 回目：書き込みの鍵（#69）をとった直後に、同じトランザクションの同じ接続で（`board/BoardIdGuard`。`WriteLockTransactionManager` が鍵のあとに呼ぶ）。理由：1 回目を前の番号で通ったあと、鍵を待っている間にテストデータの投入が終わると、そのまま書けば、投入された「番号（id）が同じ別のカード」（版も 0 どうしで見分けられない）を書き換えてしまう（CE-47b）。最初の「書き込みの最中に起きても、その書き込みごと消えるので、同じトランザクションで比べなくてよい」は、投入が先に終わる順番を見落としていた。
  - テストデータの投入（`db/seed-test-data.sql`）は、全体を 1 つのトランザクションにして、アプリと同じ鍵（`pg_advisory_xact_lock(69001)`）をとる。これで、2 回目の確かめから書き終わるまでの間に、番号が変わることはない（投入は書き込みの終わりを待ち、投入の最中に来た書き込みは投入の終わりを待ってから比べる）。
  - DB の作り直し（RDS の作り直し・`docker compose down -v`）は、アプリの起動し直し（Flyway が V6 を当て直す）を挟むので、鍵を待つ間にすれ違うことはない。
- 返事のヘッダーの番号は、2 回読んで確かめる（実装のあとのレビューで直した）。
  - Controller の前（`BoardIdInterceptor`。データを読む前）に読んで付け、読んだ番号をリクエストに覚えておく。中身のある返事は、中身を書く直前（データを読んだあと）にもう一度読む（`board/BoardIdResponseAdvice`。`ResponseBodyAdvice`）。
  - 2 回の番号が同じなら、そのまま付ける（データはそのボードのもの）。
  - **ちがえば、どの本物の番号とも一致しない値（新しく作ったランダムな UUID）を付ける**。返事を作っている間に投入がコミットされると、データが前の DB のものか新しい DB のものか、サーバーには分からないため。前の番号を付けると「新しい DB のデータ＋前の番号」（画面が帯を出せない。CE-45b）、読み直した番号を付けると「古いデータ＋新しい番号」（古い画面の入力が、番号〔id〕が同じ別のカードを版 0 どうしで黙って上書きしうる。CE-45c）になる。一致しない値なら、画面は覚えた番号とちがうので黄色の帯を出す（最初の返事でその値を覚えても、どの書き込みも 409 `BOARD_CHANGED` で止まり、帯が出る）。読み直しに失敗したときも、同じく一致しない値を付ける。
  - 最初は「読み直した番号を付け直す」にしていたが、再レビューで CE-45c の穴が見つかり、この形に直した。
  - Controller の前に付ける分は、中身を書く前に止まるエラーの返事などのために残す。中身のない返事（204）は確かめ直さない（書き込みは、鍵のあとの 2 回目の確かめで番号が合っているので、困らない）。
- テストデータの投入は、鍵のすぐあとに `LOCK TABLE board_columns, tasks, request_tokens IN ACCESS EXCLUSIVE MODE` で、書き出し（export。鍵をとらずに board_columns → tasks の順に読む）と同じ順に表をつかむ。`TRUNCATE` は tasks から先につかむので、そのままだと書き出しとデッドロック（40P01）になりうるため。あわせて `\set ON_ERROR_STOP on` で、エラーが出たらそこで止める。
- 返事のヘッダーは、Controller が決まる返事（エラーも）に付く。Controller が決まらない返事（405 の「その URL にこのメソッドはない」など。画面は送らない）には付かない。画面は、ヘッダーのない返事では比べない。
- 本番の Nginx は、`-`（ハイフン）入りのヘッダーをそのまま通す（`_` 入りは既定で落とすので、名前に `_` を使わない）。実装のときに、`http://localhost`（`docker compose --profile nginx`）で通ることを確かめる。

## 6. 画面の動き

### 6.1 共通の決まり

- **版を送る**：画面は、タスク・列の版を一覧と一緒に持ち、4.1 の表のとおり必ず送る。
- **書き込み中のカードは、返事が来るまで操作できない**（1.2 の #14）。
  - そのカードの ○・カードの ✎・× は押せず、ドラッグでつかめない。カードを少し薄く（不透明度 60%）して、送信中だと分かるようにする。
  - 対象：○（PATCH）・ドラッグ（move）・削除・編集の保存（PUT）。
  - 自動並び替え：送ったカード全部を書き込み中にし、その列の並び替えセレクトも押せなくする。また、列の中に書き込み中のカードが 1 枚でもあるあいだは、その列の並び替えセレクトを押せなくする（並べ替えはその列のカード全部の版を送るため）。
  - 列の削除：その列の × を押せなくする（今の「通信中の 2 本目を送らない」を、見た目でも分かるようにする）。
  - 理由：#69 と同じく、送信中は押せなくする。押しても何も起きない、にはしない（見た目で送信中と分かる）。
- **取り直しの決まり**（1.2 の #11）：一覧（タスク・列）の取り直しを頼んでから返事が届くまでのあいだに、この画面の書き込みの返事（成功したもの、または `current` つきの 409）を画面に入れたら、**その取り直しの返事は使わずに、もう一度取り直す**。返事が、自分の書き込みより前の状態かもしれないため。今の「最後に頼んだ取得の返事だけを使う」（#12）は、そのまま残す。
- **ドラッグのあとの確かめ**（1.2 の #12）：move の返事の `sortOrder` が、画面で落とした位置のすぐ上・すぐ下のカード（あるほう）の番号の**間に入らない**ときは、今の条件で一覧を取り直す（メッセージは出さない）。振り直しや、ほかの画面での並べ替えで、画面の番号が古くなっているため。
- **編集中のカードは、その列・位置に留める**（実装のときに足した）：✎ のフォームを開いているあいだに、カードが `current`（409）や取り直しの結果に入れ替わって別の列に移ったり、一覧から外れたりすると、カードの部品が作り直されて、フォームと入力が黙って消える。そこで、フォームを閉じるまで、カードを開いたときの列・位置に留める（中身は新しいものを見せる。一覧から外れていたら、開いたときのカードを残す）。閉じると本当の列・位置に出る（`Board.tsx` の `keepEditingInPlace`）。
  - 列も同じく留める（実装のあとのレビューで直した）：取り直し（列の削除の current なし 409 のあとの取り直しも）で、編集中のカードの列そのものがなくなる（ほかの画面で空の列が消された）と、列ごとカードの部品が消えて、フォームと入力が黙って消える。そこで、✎ を開いたときの列（と左から何番目か）も控え、その列が一覧になければ、閉じるまで同じ位置に描き続ける（`keepEditingColumn`）。
  - この形を選んだ理由：もう 1 つの案（編集フォームの入力を Board へ持ち上げ、部品が作り直されても残す）は、入力・控えた版・赤い枠の状態と、位置を測り直す仕掛けを全部動かすことになり、変更が大きい。今の形は、Board が「描く一覧」を作るところだけを変えればよく、編集中は幕で後ろを操作できないので、描き続けた列から別の操作が始まることもない。
- **編集中は、幕の後ろを操作できない**（実装のあとのレビューで直した）：幕は見た目でクリックを止めるだけなので、Tab キーで後ろのボタンへ移って押せてしまっていた。編集中は画面の本体（`#root`）を `inert`（押せない・フォーカスが入らない）にする。編集画面は `createPortal` で `#root` の外に出しているので、そのまま使える。あわせて、保存のときにそのカードがほかの書き込みの返事待ちなら、送らずに入力を残し、赤い字で「このカードは保存中です。…」と出す。
- **いまの内容がついてこない 409**（4.5 の DB の安全網。ふだんは起きない）：○・× は、今の条件で一覧を取り直して入れ替え、6.2 の文を出す。✎ の保存は、赤い枠を出せないので、ほかの失敗と同じく入力を残して、画面の上に赤い字（detail の文）を出す（次の保存で、もう一度止められたときに `current` がつく）。
- **ボードの番号**：画面は、最初に受け取った `Board-Id` を覚え、あとからちがう番号が届いても書き換えない（書き換えると、古い画面のまま新しい DB に書き込めてしまうため）。返事の `Board-Id` が覚えた番号とちがう、または書き込みが 409（`BOARD_CHANGED`）のとき、画面の上に**黄色の帯**を出し、ずっと残す。ドラッグ・自動並び替えが `BOARD_CHANGED` で止められたときは、一覧を取り直さない（新しい DB のタスクが、古い列に混ざって見えるため。帯の「読み込み直す」で読み込み直してもらう）。帯の文：「データベースが作り直されたため、この画面の内容は古くなっています。いまの内容を見るには「読み込み直す」を押してください（この画面で入力中の内容は消えます）。」と、ボタン「読み込み直す」（ページを再読み込みする）。

### 6.3 No.14②（ほかの端末の変更の自動反映）とのつながり

No.14②（再読み込みしなくても、ほかの端末での変更が画面に出る）は、**今回は作らない**。今回は「古い画面からの書き込みを止めて、知らせる」まで。古い画面は、操作してはじめて「変わっていた」と分かる。

将来 No.14② を作るときは、次をそのまま使う。

- 届いた変更と画面の持っているものを比べるときは、**版の大きいほうが新しい**（届いた版が画面の版以下なら捨てる）。
- 編集フォームを開いているカードに変更が届いたら、6.2 の赤い枠を、保存を押す前から出せる（入力は残したまま）。
- ボードの番号が変わったら、6.1 の帯を出す。
- 6.1 の「取り直しの決まり」は、届いた変更の入れ方にも使える。

## 7. 確かめる場面

## 8. 作らないもの・後回し

| もの | 理由 |
| --- | --- |
| ほかの端末の変更の自動反映（No.14②） | 要件定義書 No.14 で「やり方は、実装するときのイシューで決める」としていて、今回の範囲（黙って上書きしない）より大きい。つながりは 6.3 に書いた |
| 項目ごとの自動マージ（方式の⑧） | 1 行に 1 つの版なので、関係ない項目の変更（並びだけ変わった、など）でも止まる。ただし入力は残り、いまの内容を見て「この入力で上書き保存」を 1 回押せば済み、データは失われない。マージには項目ごとの履歴が要り、作りが大きい。止まるのが多くて困るようになったら、要件定義書 5.2 節に足して決める |
| 版を送らない書き込みの後勝ち | 4.1 のとおり、版は省略できる（API を直接呼ぶ人・今のテスト・デプロイのときに開いたままの古い画面のため）。画面は必ず送るので、画面からの操作では後勝ちは起きない |
| import の版での確かめ | 全部を置き換えることが目的で、確認のダイアログで伝えている（1.3）。古い画面からの import も、ボードの番号（5 節）は確かめる |
| 列の名前の変更・並べ替えの画面 | 今も画面がない（API だけ）。API には版の確かめを入れる（CE-10・29・31） |
| 消された列へのタスクの追加の知らせの言い方 | 今も 400 で止まり、入力は残り、理由（「id が … の列はありません」）も出るので、データは失われない。言い方を「ほかの画面で消された」に変えるには、400 の理由を見分ける印が要る。困るようになったら決める |
| 画面のテスト（CE-50〜67） | 画面のテストの仕組みがない。要件定義書 No.27 で、取り直しの決まり（6.1）・ドラッグのあとの確かめ（6.1）・409 の扱い（6.2）から画面のテストにする |
| だれが変えたかの表示・変更の履歴・元に戻す | ログイン（利用者）がなく、1 人で使うアプリのため |
