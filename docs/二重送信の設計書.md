# 二重送信・同時操作の設計書（イシュー #69）

2 回届いた・同時に届いた通信でも、**データが 2 件にならない・500 のエラー画面にならない・「失敗」と、まちがった知らせが出ない**ようにするための決まりと、確かめる場面の一覧。

全アプリのレビュー指摘の洗い直し（2026-11-07）で、「二重送信」の同じ形が taskmanagement に残っていると分かったので直す。ほかのアプリ（SNS・kakeibo）が使っている「番号札」と同じ考え方にそろえる。

## 1. 直すもの（現状と決めたこと）

| # | 現状 | 決めたこと（ユーザー決定 2026-11-07） |
| --- | --- | --- |
| 1 | タスク・列の削除の 2 回目が 404 になり、画面に赤い「削除できませんでした」が出る（実際は消せている） | **削除は、すでにない番号でも 204（成功）にする**。画面も、404 が来たら成功と同じに扱う（更新・完了と同じ） |
| 2 | タスク・列の追加に二重送信の防ぎがなく、返事が届かなかったときに押し直すと 2 件できる。ボタンも送信中に押せる | **番号札（`Idempotency-Key`）を入れる**。画面は、追加のたびに札を作って送り、**送信中はボタンを押せなくする** |
| 3 | 追加が失敗すると、入力した文章が戻らない | 失敗したら、**入力（文章・優先度・期限）を戻し**、同じ札で送り直せるようにする |
| 4 | import を同時に 2 本送ると、2 本目が「完了の列は 1 つだけ」の制約に当たって 500 になる見込み。import 中の追加・列の削除も、列が消えて 500 になりうる | **書き込みをひとつずつ順番に処理する**（DB の `pg_advisory_xact_lock`）。import が 2 本重なっても、あとから終わったほうの内容が残り、どちらも成功する |
| 5 | 同時に作ると、並び順の数字が同じになりうる。同じ数字のとき、並びが決まっていない | 並べるときの第 2 のキーに id を足して、並びを安定させる |

**別にするもの**：同時に変えたときの後勝ち（#21・要件定義書 No.24）は、版（version）の列の追加まで及ぶ大きな直しなので、別のイシュー・PR にする。

## 2. 番号札の決まり

- 対象：`POST /api/tasks`（タスクの追加）と `POST /api/columns`（列の追加）。
- 札は、リクエストヘッダー `Idempotency-Key`（UUID）。**札がないときは、今までどおり**（毎回新しく作る）。API を直接呼ぶ人・今のテストを壊さないため。画面は必ず付ける。
- 札と中身の指紋（本文の SHA-256）を、新しい表 `request_tokens`（V5）に、追加と**同じトランザクション**で記録する（追加だけ残って札がない・札だけ残って追加がない、にならない）。
- 表 `request_tokens` の列：`token`（UUID・主キー）、`kind`（`'task'` か `'column'`）、`resource_id`（BIGINT。作ったタスク・列の番号。追加の途中は NULL を許す）、`fingerprint`（CHAR(64)。中身の SHA-256 を 16 進にしたもの）、`created_at`（TIMESTAMPTZ・NOT NULL・既定は now()）。
- 中身の指紋に入れるもの：タスクは「文章（前後の空白を除いたもの）・優先度（省略は medium として）・期限・列の番号（省略は一番左の列として）」、列は「名前（前後の空白を除いたもの）」。
- 同じ札が来たとき：
  - 中身の指紋が同じ → **1 回目と同じ結果（201 と同じ内容）を返す。新しくは作らない**。
  - 中身の指紋がちがう → **409**（「同じ番号札で、ちがう内容が送られました」）。
  - 1 回目に作ったものが、そのあと消されている → **404**（新しく作り直さない。消した人の意思を戻さない）。
- 同じ札が同時に 2 本来たら、先に入れたほうだけが作り、あとのほうは先のコミットを待って、同じ結果を返す（`INSERT … ON CONFLICT DO NOTHING` で、あとのほうは待つ）。
- 札が UUID でない → 400。
- 古い札の掃除：作成から **24 時間をこえた札**は、追加のたびに消す（専用の定期処理は作らない。札を消したあとに同じ札が来たら、新しいものとして作る。24 時間あとの再送は想定しない）。

## 3. 削除の決まり

- `DELETE /api/tasks/{id}`・`DELETE /api/columns/{id}`：**すでにない番号でも 204**。
- 打ち間違いの番号（一度もなかった番号）も 204 になる。見分けられないが、削除は「結果がなくなっていること」が目的なので、これを許す。
- 列の削除で、列が**ある**ときの 409（基本の列・タスクが入っている列）は、今のまま。

## 4. 書き込みの順番

- 書き込む処理（追加・更新・完了・移動・並べ替え・削除・列の操作・import）の頭で、`pg_advisory_xact_lock`（アプリ全体で 1 つの鍵）をとる。トランザクションの終わりに自動で外れる。
- このアプリは、1 人で使う小さなボードなので、書き込みを 1 つずつにしても、待ちは気にならない（数ミリ秒）。
